# Portal-template implementation plan

## Phase 1 — Capture the reusable contract

Maintain this requirements pack and operator runbook alongside canonical participant guides. Link them from the portal and agent index. Keep known gaps explicit. Reuse the existing portal; do not generate a second documentation system.

## Phase 2 — Prepare a releaseable starter

Choose a tested source revision, remove event-specific assumptions from configurable surfaces, lock toolchain/dependencies, retain licensing and asset provenance, and validate a clean clone with initialized submodule. Add a source provenance record per event. Publish a starter tag only after authorized review and DCO checks.

## Phase 3 — Prove the participant path

Complete baseline runtime gates before expanding challenges. Add namespaced scaffolding and dispatch with overwrite guards and inherited capability tests. Rehearse one team fork, metadata preparation, evidence recording and a metadata-only registration branch.

## Phase 4 — Enable registry publication

Finalize the manifest schema. Implement bounded public-source resolution, evidence/consent review and project/state rendering. Add negative fixtures before removing the empty-registry guard. Establish real fork-preview behavior. Featured preservation follows as a separate capability.

## Phase 5 — Rehearse and operate an event

Run the acceptance matrix with a newcomer, assign operators, document support and rollback, then open registration at the supported level. Freeze the event edition and review handover after the event.

Dependencies: roadmap #1 coordinates the sequence; generation #2, registry #3, portal #4, hosting #5, rehearsal #6 and governance #7 remain distinct workstreams. Operator documentation can be delivered before these capabilities are complete, but must not claim their completion.
